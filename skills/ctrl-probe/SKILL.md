# CTRL Probe

## 시작: 지금 일어나는 일을 먼저 확인

사용자가 본 증상과 방금 한 물리 조작을 현재 입력으로 삼는다. 처음에는 문제를 보인 화면·장비에서
가장 가까운 **생산자 → 전송 → 소비자** 경계 하나를 고른다. 센터 보고 문제라면 센터 Tx/Rx,
HILSS 점등 문제라면 실제 HILSS 프로세스와 해당 COM·CID 응답부터 본다. 전체 체인 수집이나
소스 역분석을 기본 절차로 시작하지 않는다. 수집·재분석은 함께 제공한 `scripts/observe.py --help`의 공개 인자를 사용한다.

새 세션에서 이어가거나 인계 자료를 찾을 때는 [ACCESS.md의 협업 문서 위치](ACCESS.md)를
따라 작업 환경의 협업 `README.md`, `CURRENT.md`와 해당 과업의 최신 `runs/` 기록을 함께 읽는다.
`CURRENT.md`에 아직 연결되지 않은 후속 기록이 있을 수 있으므로 파일 목록·수정 시각도
대조한다. 완료·원복·미확정 상태는 기록의 마지막 결과와 근거에서 확인하고, 현재 설정·
flashed build·실행 세대는 재조회한다. 로컬 handoff는 작성 시점의 비정본 스냅샷이다.

짧은 첫 관측에서 다음을 함께 기록한다.

1. 현재 실행 위치·프로세스 PID/시작 시각·실행 파일, 실제 포트/peer 및 관측 시각. 재시작·케이블
   변경 뒤에는 이전 세대의 포트 대응과 상태를 현재 사실로 쓰지 않는다.
2. 같은 구간의 실제 입력과 출력. 접속 성공, 명령 송신, 응답 수신, 해석값, 화면 표시는 각각
   구분한다. 로그의 기존 행이 아닌 관측 구간 증가분을 읽고 원문·수집 공백을 보존한다.
3. 사용자가 말한 `OFF`·`무응답`이 어느 경계의 값인지 확인한다. 예를 들어 CID의 CAN 단선,
   `BB→BA` 직렬 응답, HILSS의 해석 상태, B8 출력은 서로 다른 상태다.

곧바로 `확인된 상태 / 아직 구분되지 않은 경계 / 가장 작은 다음 관측 또는 정상 조치`를 알린다.
원인 가설이 하나로 좁혀지면 필요한 근거만 더 모은다. 수집 실패·권한 부족을 장비 무응답으로
판정하지 않는다. 패킷 값이 일정한 것만으로 독립 생성이나 GUI 점등의 원인을 확정하지 않는다.

## 관측 경로 선택

- **센터↔두 제어기:** 현재 identity·peer·HOST/COMM 실행 세대를 확인하고
  `scripts/observe.py capture`로 관련 두 peer의 명시한 센터 TCP 포트을 같은 구간에 수집한다.
  `observe.py analyze`의 재조립 frame과 원문을 대조한다. Tx 차이를 먼저 확인하고 0x23은
  동일 집계구간이 확인된 뒤 비교한다. 설정 적용이 의심되면 DB 스냅샷과 HOST·COMM 실제
  소비값의 갱신 세대를 연결한 뒤 펌웨어 원인을 논한다.
- **HILSS↔CID 또는 화면 점등:** 실제 Windows 세션·실행 중 인스턴스·COM 핸들을 확인한다.
  `hCID`, `hCIDSingle`, `hCAP`을 별도 경로로 취급한다. 해당 구간의 직렬 TX/RX 원문과
  Det/Sig 로그, 필요하면 해석 메모리를 같은 시간축에 맞춘다. HILSS 내부 생성값과 CID 입력값,
  출력 프레임과 GUI 표시를 혼동하지 않는다.
- **물리 CAN/CID 입력:** 앞 경계에서 남은 가설을 가를 수집점만 선택한다. 어느 케이블을
  뺐는지, 장치 전원과 다른 통신 경로가 계속 살아 있는지를 먼저 확인한다. 현재 두 제어기
  A/B 시험에는 [ACCESS.md의 CAN 로그 경로](ACCESS.md)를 사용한다. 이미 연결된 네 수집
  스트림은 센터 파일에서 읽고, 기존 단일 캡처 클라이언트가 사용 중인
  리스너에 새로 접속하지 않는다.

사용자가 **의도부터 결과까지** 비교하라고 요청하면 같은 시험 구간에서 센터 명령 Tx,
두 장비의 CAN1 출력·피드백과 CAN2 입력, 센터 보고 Rx를 사건으로 연결한다. 결과가 MMI
화면이면 표시 수신·표현도 확인한다. 네 CAN 덤프만으로 센터가 같은 명령을 보냈는지,
MLC가 어떻게 보고했는지, MMI가 무엇을 표시했는지는 증명할 수 없다. 서로 다른 업체의
CAN payload는 바이트 동일성보다 해석된 신호·검지 사건의 동등성으로 비교한다.
파일의 태그만으로 물리 어댑터↔버스 대응을 확정하지 않고, 수집기의 drop·재연결·시계와
각 로그의 session marker를 함께 확인한다.

접속 주소·계정·키 경로·로그 위치는 [공개용 환경 바인딩](ACCESS.md)에 따라 작업 환경에서 지정한다.
주소가 바뀌면 대상 신원을 재확인하며, 실패한 원격 명령은 적용 여부를 확인하기 전에 자동 재실행하지 않는다.

## 판단과 대응

- 현재 관측으로 처음 어긋난 경계를 명시한다. 그 이전이 미관측이면 `최초 분기`라고 하지 않는다.
- 소스·과거 로그는 현재 바이너리 hash와 실행 세대가 맞을 때만 현재 원인 판단에 쓴다.
- 이미 승인된 정상 조치가 있으면 영향 범위를 확인하고 수행한 뒤 같은 경계를 다시 관측한다.
  임의 메모리 패치, firmware 변경, CAN TX, CID 자극, reset·재기동은 구체적인 사용자 요청
  또는 기존 승인 범위가 있을 때만 한다.
- 사람에게는 현재 상태·확정한 원인 또는 한계·실행한 조치와 다음 최소 행동만 전달한다.

디코더가 해석하는 범위와 근거의 한계는 [수집·해석 범위](references/protocol.md)에서 확인한다.
